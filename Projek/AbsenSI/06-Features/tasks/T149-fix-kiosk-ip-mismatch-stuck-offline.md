# T149 — API+Kiosk+Web: Fix Kiosk Stuck "Memuat Konfigurasi Mesin" Akibat IP Mismatch (Bedakan dari Offline Sungguhan)

## Depends on
Tidak ada dependency teknis. Independen, PRIORITAS TINGGI (bug produksi aktif dilaporkan user 2026-08-09 — "beberapa mesin menampilkan pesan offline padahal server online, dengan icon loading 'Memuat Konfigurasi Mesin'").

## Objective
1. Kiosk yang ditolak server karena IP-nya sudah tidak cocok dengan `allowedIp` terdaftar (403) **TIDAK LAGI** ditampilkan sebagai "sedang memuat/menghubungkan" yang terus retry tanpa akhir — melainkan pesan jelas yang membedakan kondisi ini dari offline/jaringan-mati sungguhan.
2. Admin punya jalan CEPAT dan JELAS untuk melihat kiosk mana yang IP-nya mismatch dan memperbaikinya, TANPA perlu akses log server (SSH/journalctl).

## Context — Diagnosis Dikonfirmasi (Riset 2026-08-09, Baca Kode Langsung)

**Ini BUKAN regresi/kambuhnya bug T131** (yang soal timeout/race saat fetch gagal karena network down sungguhan — fix T131 tetap valid untuk kasus itu). Ini KELAS BUG BERBEDA yang KEBETULAN menampilkan gejala visual sama (badge "Memuat Konfigurasi Mesin..." yang ditambahkan fix T131) karena kode saat ini tidak membedakan 2 penyebab berbeda:

**Akar masalah**: `KioskGuard` (`apps/api/src/auth/guards/kiosk.guard.ts:46-49`) menolak request dengan **403 Forbidden** kalau `clientIp !== kiosk.allowedIp` (exact string match) — dipakai di endpoint `GET /kiosks/me` (dipanggil `fetchKioskInfo()` di kiosk-app) DAN endpoint `POST /api/tap`. User mengonfirmasi IP kiosk **SEHARUSNYA statis** (bukan DHCP dinamis) — jadi validasi keamanan IP itu SENDIRI tetap benar dan TIDAK diubah oleh task ini. Masalahnya murni bagaimana KEGAGALAN ini ditangani di sisi tampilan:

- `apps/kiosk/src/app/page.tsx:93` — `const info = res.ok ? await res.json() : null;` — respons 403 (config salah, butuh intervensi admin) diperlakukan **SAMA PERSIS** seperti gagal-koneksi/timeout (kondisi sementara yang wajar di-retry). `kioskInfo` di-set `null` untuk KEDUA kasus.
- `kioskInfo === null` memicu badge **"Memuat konfigurasi mesin..."** (dari fix T131) yang tampil terus dan RETRY OTOMATIS tiap ±20 detik (efek ping) — tapi untuk kasus IP mismatch, **retry ini TIDAK PERNAH BISA BERHASIL** (IP tetap sama, tetap ditolak) — sehingga badge itu **stuck permanen**, bukan sementara seperti niatnya di T131.
- **Kenapa server terlihat "online"**: ada 2 mekanisme deteksi terpisah dan tidak saling terhubung — `/health/time` (`apps/api/src/health/health.controller.ts:9-15`) TANPA guard sama sekali, selalu 200 OK selama proses server hidup, dipakai untuk badge `serverReachable`. Sedangkan `kioskInfo`/tap SELALU lewat `KioskGuard` yang bisa 403. Dua sinyal ini independen — bisa "server online" (benar) DAN "kiosk ini ditolak" (juga benar) muncul BERSAMAAN, terlihat kontradiktif ke user.
- **Kenapa "offline — N tap tersimpan lokal" juga muncul bersamaan**: `POST /api/tap` (`apps/kiosk/src/app/api/tap/route.ts:23-31`) memakai `KioskGuard` YANG SAMA — jadi tap SISWA/GURU juga ikut ditolak 403, gagal terkirim, otomatis masuk buffer offline lokal (`bufferTap`), `pendingCount` naik, banner "Offline" ikut tampil. Ini menjelaskan PERSIS kenapa user melihat KEDUA pesan sekaligus di mesin yang sama.
- **Kenapa cuma "beberapa mesin"**: `allowedIp` di-set sekali saat registrasi kiosk. Kiosk yang jaringannya berubah (WiFi vs LAN, router di-reset, dst — walau harusnya statis, kejadian teknis bisa mengubahnya) jadi tidak cocok lagi; kiosk lain yang IP-nya tidak pernah berubah tidak kena. Ada PRESEDEN insiden serupa sebelumnya (komentar kode `kiosks.controller.ts:31-38`, tanggal 2026-07-26).

**Gap tambahan yang ditemukan** (riset UI admin, 2026-08-09):
- Halaman admin `apps/web/src/app/(admin)/kiosk/kiosk-view.tsx` MENAMPILKAN `allowedIp` di tabel (baris ±137) dan BISA diubah lewat form edit (`PATCH /kiosks/:id`) — jadi mekanisme UPDATE sudah ada, TAPI:
  - Blok bantuan "Deteksi IP Otomatis" (baris ±312-331) HANYA muncul di mode **create**, TIDAK muncul di mode **edit** (baris ±281) — padahal skenario "IP sudah berubah, kiosk sudah terdaftar, perlu di-update" JUSTRU butuh mode edit. Yang ada cuma 1 baris hint teks pasif (baris ±347-353), tidak actionable.
  - Kolom Status (baris ±138-154) cuma render Online/Offline generik, TIDAK PERNAH menyebut kemungkinan IP mismatch sebagai penyebab — admin tidak dapat petunjuk apa pun harus curiga ke arah mana.
  - Field `Kiosk.lastSeenIp`/`lastSeenAt` (schema.prisma:594-614) HANYA ter-update di JALUR SUKSES (`kiosk.guard.ts:53-56`, SETELAH IP check lolos, `catch(() => {})` fire-and-forget) — begitu mismatch mulai terjadi, field ini **MEMBEKU** di IP lama yang terakhir berhasil, TIDAK BISA dipakai menunjukkan IP kiosk yang sebenarnya SEKARANG.
  - Tidak ada field `lastFailedIp`/`lastFailedAt` untuk menyimpan "IP yang barusan ditolak" — ini gap paling langsung untuk diperbaiki.
  - Endpoint `GET /kiosks/detect-ip` (`kiosks.controller.ts:40-43`) SUDAH ADA, publik (tanpa guard, sengaja untuk chicken-and-egg saat kiosk belum terdaftar), memakai `extractClientIp()` YANG SAMA PERSIS dengan yang dipakai `KioskGuard` — jadi hasilnya DIJAMIN akurat untuk dibandingkan. Reusable, tapi saat ini MURNI PASIF (kiosk-app punya halaman `/deteksi-ip` yang tampilkan IP besar-besar untuk DICATAT MANUAL oleh petugas) — TIDAK ADA mekanisme "kiosk lapor IP-nya sendiri ke record dirinya" untuk self-diagnosis otomatis.
- **Tidak ada sistem notifikasi apa pun** untuk kondisi ini (dikonfirmasi riset menyeluruh) — admin harus PROAKTIF membuka halaman Kiosk dan curiga manual, tidak ada dorongan/sinyal aktif.
- IP mismatch TIDAK PERNAH tercatat ke `ActivityLog` (guard melempar exception SEBELUM controller manapun jalan, jadi `@LogActivity` decorator tidak pernah tereksekusi) — satu-satunya jejak adalah `Logger.warn` di `kiosk.guard.ts:47-49`, HANYA bisa dilihat lewat akses server langsung (SSH/journalctl), TIDAK ADA UI yang membacanya.

## Spec Detail

### 1. Backend — `Kiosk` schema: tambah field untuk menyimpan IP yang DITOLAK

```prisma
// Tambah ke model Kiosk yang sudah ada:
lastFailedIp  String?   @map("last_failed_ip") @db.VarChar(45)
lastFailedAt  DateTime? @map("last_failed_at")
```
- Migration baru.
- **`KioskGuard`** (`kiosk.guard.ts:46-51`) — SEBELUM `throw new ForbiddenException(...)`, tulis (fire-and-forget, SAMA POLA seperti update `lastSeenAt/lastSeenIp` yang sudah ada di jalur sukses — jangan `await`, jangan sampai memperlambat/menggagalkan response error) `lastFailedIp: clientIp, lastFailedAt: new Date()` ke baris `Kiosk` itu. Ini memberi admin data KONKRET "IP yang barusan mencoba akses tapi ditolak", TANPA perlu akses log server.

### 2. Backend — bedakan response 403 IP-mismatch dari error lain

- Pastikan `ForbiddenException` yang dilempar `KioskGuard` untuk kasus IP mismatch punya PESAN/KODE yang bisa dibedakan frontend dari kegagalan lain (misal device token invalid, kiosk nonaktif — cek apakah `KioskGuard` juga menangani kasus-kasus itu dan pastikan pesannya BERBEDA per kasus, bukan 1 pesan generik untuk semua alasan penolakan). REKOMENDASI: sertakan properti terstruktur di response body exception (misal `{ statusCode: 403, error: "IP_MISMATCH", message: "..." }`) supaya frontend bisa switch berdasarkan `error` code, bukan parsing string pesan yang rapuh.

### 3. Kiosk-app — bedakan penanganan 403 IP-mismatch dari kegagalan network

- `apps/kiosk/src/app/page.tsx` (`fetchKioskInfo()`, sekitar baris 93) — JANGAN lagi perlakukan SEMUA `!res.ok` sebagai `null` generik. Cek status code: kalau **403 dengan kode `IP_MISMATCH`** (dari poin 2) → set state BARU yang BERBEDA dari `kioskInfo === null` biasa, misal `kioskConfigError: "ip_mismatch"`.
- **UI baru untuk kondisi ini** — GANTI badge "Memuat konfigurasi mesin..." (yang menyiratkan "sedang proses, tunggu sebentar") dengan pesan JELAS DAN BERBEDA: sesuatu seperti *"Mesin ini tidak dikenali server (alamat jaringan berubah) — hubungi admin untuk memperbarui pengaturan."* — TIDAK menyiratkan akan pulih sendiri, karena memang TIDAK AKAN (retry tidak akan pernah berhasil sampai admin update `allowedIp`).
- **JANGAN hapus retry loop untuk kasus TIMEOUT/network-down sungguhan** (itu tetap valid, fix T131 tetap dipertahankan apa adanya untuk skenario itu) — task ini HANYA menambah CABANG BARU untuk kasus 403 IP-mismatch yang butuh perlakuan berbeda, bukan mengganti mekanisme lama.
- Proxy route `apps/kiosk/src/app/api/kiosk-info/route.ts` (baris ±15-24) — pastikan status code DAN body JSON dari backend (termasuk `error: "IP_MISMATCH"` dari poin 2) diteruskan apa adanya ke frontend, JANGAN di-strip.
- `POST /api/tap` (`apps/kiosk/src/app/api/tap/route.ts:23-31`) — kena guard yang sama, SETELAH poin 2 selesai, request tap yang gagal karena IP mismatch JUGA sebaiknya masuk kategori berbeda dari "gagal network biasa" di banner offline (opsional, evaluasi saat implementasi apakah worth dipisah juga di banner "Offline — N tap tersimpan lokal", atau cukup badge kioskConfigError di atas sudah cukup menjelaskan akar masalah tanpa perlu duplikasi pesan di 2 tempat — REKOMENDASI: cukup 1 pesan jelas di badge utama, banner offline boleh tetap generik karena user sudah dapat penjelasan dari badge utama).

### 4. Frontend Admin — halaman Kiosk (`kiosk-view.tsx`) tampilkan sinyal IP-mismatch jelas

- Tabel daftar kiosk (baris ±137-154) — TAMBAH indikator visual (badge/warna) KETIKA `lastFailedIp` (dari poin 1) ADA NILAI DAN berbeda dari `allowedIp` DAN `lastFailedAt` lebih baru dari `lastSeenAt` (menandakan kegagalan BARU-BARU INI, bukan histori lama yang sudah diperbaiki) — misal badge kuning/merah "IP Tidak Cocok" di samping status Online/Offline, dengan tooltip/detail menampilkan `allowedIp` (terdaftar) vs `lastFailedIp` (yang ditolak barusan).
- Form edit kiosk — TAMBAHKAN blok bantuan "Deteksi IP Otomatis" yang SAMA seperti di mode create (baris ±312-331), JANGAN dibatasi `mode === "create"` saja — buat kondisinya juga true untuk mode edit, supaya admin yang sedang memperbaiki IP kiosk existing dapat alat bantu yang sama persis.
- Pre-fill form edit — kalau `lastFailedIp` tersedia dan admin membuka form edit kiosk yang bermasalah, PERTIMBANGKAN tampilkan `lastFailedIp` sebagai SARAN nilai baru untuk field `allowedIp` (misal tombol kecil "Gunakan IP terdeteksi: X.X.X.X" yang mengisi field otomatis kalau diklik) — mempercepat alur perbaikan admin dari "lihat masalah" ke "perbaiki" dalam 1 halaman, tanpa perlu bolak-balik ke halaman `/deteksi-ip` kiosk fisik.

## Edge Cases
- Kiosk yang `lastFailedIp` terisi TAPI masalahnya SUDAH diperbaiki (admin sudah update `allowedIp`, kiosk sudah online lagi) — badge "IP Tidak Cocok" TIDAK BOLEH terus muncul selamanya (histori lama). Bedakan dengan cek `lastSeenAt > lastFailedAt` (kalau kiosk berhasil konek SETELAH kegagalan terakhir, berarti sudah pulih) — kalau begitu, JANGAN tampilkan badge (atau tampilkan versi redup "pernah bermasalah, sudah pulih").
- Kiosk yang BELUM PERNAH konek sama sekali (baru didaftarkan, `lastSeenAt` dan `lastFailedAt` keduanya null) — TIDAK ADA badge apa pun (state normal "belum pernah terhubung", bukan error).
- IP mismatch terjadi bersamaan dengan alasan penolakan LAIN (device token dicabut, kiosk dinonaktifkan `isActive: false`) — pastikan `KioskGuard` MEMBEDAKAN kode error untuk masing-masing alasan (poin 2), supaya frontend tidak salah menampilkan pesan "IP tidak cocok" untuk kasus yang sebenarnya penyebabnya beda (misal token dicabut).
