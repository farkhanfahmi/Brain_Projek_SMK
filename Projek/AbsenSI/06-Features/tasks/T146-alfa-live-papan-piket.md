# T146 — API+Web: Kategori "Alfa" Real-Time di Papan Piket (Live, Bukan Cuma Rekap)

## Depends on
**WAJIB T144 (fix bug alfa=0) DAN T145 (jam masuk 3-lapis) selesai dan diverifikasi dulu.** T146 memakai `resolveJamMasuk()` dari T145 sebagai sumber deadline, dan bergantung pada `resolveHariWajib()` yang sudah diperbaiki sinyalnya di T144. JANGAN mulai task ini sebelum keduanya selesai.

## Objective
Papan piket (`piket-board-view.tsx`, tampilan LIVE hari berjalan) menampilkan kategori status BARU "Alfa" untuk siswa yang belum tap SAMPAI jam masuk (sesuai kelasnya, hasil resolusi 3-lapis T145) sudah lewat DAN belum ada izin/sakit — murni tampilan real-time terhitung (BUKAN status tersimpan di DB), konsisten prinsip permanen proyek "Alfa bukan kolom DB". Begitu siswa tap (walau telat) → otomatis pindah kategori jadi "Terlambat". Begitu piket tandai izin/sakit → otomatis pindah kategori jadi "Izin"/"Sakit". Semua transisi terjadi live tanpa refresh manual (reuse mekanisme Socket.IO yang sudah ada).

## Context — Kenapa Task Ini Terpisah dari T144

User (2026-08-08) awalnya melaporkan bug alfa=0 di REKAP, lalu saat didiskusikan solusinya, mengusulkan logic "siswa belum tap sampai jam mulai → langsung dianggap Alfa, tap belakangan → jadi Terlambat, izin/sakit → jadi Izin/Sakit" — dan mengonfirmasi eksplisit ini **logic utama** yang diinginkan berlaku di REKAP **dan** LIVE (papan piket hari berjalan), bukan cuma salah satunya.

**PENTING — task ini TIDAK mengubah arsitektur data**: efek "alfa → terlambat → izin" yang diminta user SUDAH otomatis terjadi di REKAP begitu T144 selesai (karena rekap murni kalkulasi ulang setiap kali dibuka — begitu siswa akhirnya tap, rekap berikutnya otomatis menunjukkan "Terlambat" bukan "Alfa" untuk siswa itu, tanpa perlu logic tambahan). Yang BELUM ada dan JADI SCOPE task ini murni: **tampilan LIVE di papan piket** (dashboard hari berjalan) belum punya kategori "Alfa" sama sekali (baca Context riset di bawah) — task ini MENAMBAHKAN kategori itu ke tampilan live, TETAP sebagai nilai TERHITUNG (computed), bukan status baru yang disimpan ke `AttendanceRecord`.

## Riset Terkonfirmasi (2026-08-08)

- **Board utama saat ini** (`AttendanceService.piketBoard()`, `apps/api/src/attendance/attendance.service.ts:333-380`, endpoint `GET` di `AttendanceController` baris 175-176) — field `status` per siswa **LANGSUNG dari `record?.status ?? null`** (baris 366), TIDAK dihitung ulang. `status: null` berarti "belum ada `AttendanceRecord` hari ini".
- **Frontend `StatusBadge`** (`piket-board-view.tsx:119-164`) — urutan prioritas render: Terkunci → Belum Memiliki Kartu → Izin/Sakit → Terlambat → Hadir (baris `hadir` DISEMBUNYIKAN dari tabel via filter `visibleBoard`, baris 221) → fallback **"Belum Hadir"** (untuk `status: null` DAN semua kondisi lain gagal). **Tidak ada kategori "Alfa" sama sekali saat ini** — "Belum Hadir" adalah kondisi generik yang MENCAMPUR "belum tap tapi jam belum lewat" dengan "belum tap dan jam SUDAH lewat" (yang seharusnya beda kategori menurut permintaan user).
- **Update real-time SUDAH ADA dan REUSABLE**: `useAttendanceSocket` (`piket-board-view.tsx:237-255`) — event `onKampusUpdate` update `status`/`waktuMasuk` per `studentId` begitu siswa tap. `handlePermitSubmitted()` (baris 257-262) — update `status` client-side jadi `"izin"/"sakit"` begitu piket submit form izin. **KEDUA mekanisme ini SUDAH otomatis membuat kondisi "Alfa" gugur** begitu salah satu terjadi (`status` jadi non-null) — task ini TIDAK PERLU membangun mekanisme transisi baru, CUKUP menambah 1 kategori tampilan yang dievaluasi ULANG setiap render/update.
- **Sumber deadline jam masuk**: `Schedule{type:jam_sekolah}` — SEBELUM T145, ini 1 baris global tanpa filter kelas (BUG). **SETELAH T145 selesai**, `ScheduleService.resolveJamMasuk(kelasId, hari)` adalah SUMBER TUNGGAL yang WAJIB dipakai task ini — supaya deadline "Alfa" untuk siswa kelas tertentu PERSIS SAMA dengan deadline yang menentukan status "Terlambat" siswa itu saat akhirnya tap (`determineStatus()`, sudah diperbaiki T145 memakai `resolveJamMasuk()` juga) — **KONSISTENSI INI KRITIS**: kalau live-Alfa pakai sumber deadline BERBEDA dari `determineStatus()`, akan ada celah waktu di mana siswa terlihat "Alfa" di board tapi begitu tap malah jadi "Hadir" (bukan "Terlambat") karena deadline yang dipakai beda — WAJIB 1 sumber kebenaran yang sama persis.
- **TANPA toleransi tambahan** — `determineStatus()` (setelah T145) pakai `jamMulai` PERSIS (tanpa `+toleransi`) untuk menentukan Terlambat. Live-Alfa board **WAJIB pakai deadline yang SAMA PERSIS** (`jamMulai` tanpa toleransi) — JANGAN mencontoh pola `hitungGuruBelumMulai()` (`TvPiketService`, dipakai untuk GURU) yang pakai `ScheduleConfig.toleransiTerlambatMenit` — itu konteks berbeda (guru), TIDAK berlaku untuk siswa.
- **Guard hari wajib WAJIB dipakai** — kalau hari ini BUKAN hari wajib (weekend/libur/tidak ada AcademicYear aktif SETELAH T144 fix) — board TIDAK BOLEH menampilkan kategori "Alfa" sama sekali (bukan Alfa untuk semua siswa yang belum tap, karena mungkin memang hari libur). Reuse `resolveHariWajib()` (SUDAH diperbaiki T144, punya sinyal `adaTahunAjaranAktif` terpisah) — panggil untuk TANGGAL HARI INI saja (`from === to === hari ini`), kalau `wajibDates.size === 0` (baik karena libur MAUPUN karena tidak ada tahun ajaran aktif), board TIDAK menampilkan kategori Alfa (fallback ke "Belum Hadir" seperti sekarang, aman untuk kedua kasus).
- **Timezone**: ada 2 implementasi `combineDateAndTime()` berbeda di codebase — versi `attendance.service.ts` pakai `setHours()` (LOCAL time), versi `tv-piket.service.ts` pakai `setUTCHours()` (UTC). Task ini **WAJIB pakai versi LOCAL TIME** (konsisten dengan `determineStatus()`/`resolveJamMasuk()` yang jadi sumber kebenaran) — JANGAN reuse helper UTC dari `TvPiketService` untuk fitur ini, itu akan menghasilkan deadline yang salah kalau server tidak berjalan di UTC.

## Spec Detail

### 1. Backend — `AttendanceService.piketBoard()` — tambah field terhitung

- Untuk SETIAP siswa di board (baris 333-380), setelah ambil `record?.status ?? null` (baris 366) SEPERTI SEKARANG (TIDAK diubah, field `status` mentah TETAP dikirim apa adanya) — TAMBAH field BARU di response: `kategoriLive: "hadir" | "terlambat" | "izin" | "sakit" | "alfa" | "belum_hadir"` — computed di backend SEKALI per request (bukan diserahkan ke frontend untuk hitung ulang, supaya 1 sumber kebenaran):
  ```
  kalau status !== null → kategoriLive = status (hadir/terlambat/izin/sakit, seperti biasa)
  kalau status === null:
    kalau HARI INI bukan hari wajib (wajibDates kosong, dari resolveHariWajib) → kategoriLive = "belum_hadir" (TIDAK PERNAH "alfa" di hari non-wajib)
    kalau siswa belum punya kartu aktif (belumMemilikiKartu true) → kategoriLive = "belum_hadir" (TIDAK "alfa" — siswa yang belum dikasih kartu bukan salahnya sendiri, kategori berbeda sudah ada "Belum Memiliki Kartu" dengan prioritas lebih tinggi, JANGAN timpa itu)
    kalau now > resolveJamMasuk(student.kelasId, hariIni).jamMulai (pakai LOCAL time combineDateAndTime) → kategoriLive = "alfa"
    kalau tidak (masih sebelum jam masuk) → kategoriLive = "belum_hadir"
  ```
- **Panggil `resolveJamMasuk()` (T145) SEKALI per KELAS UNIK yang muncul di board** (bukan per siswa — banyak siswa berbagi kelas yang sama), simpan di `Map<kelasId, jamMulai>` untuk efisiensi query, MIRIP pola yang direkomendasikan riset T145 untuk `determineStatus()`.
- `resolveHariWajib()` dipanggil SEKALI untuk `(hariIni, hariIni)` di awal method, hasilnya dipakai untuk SEMUA siswa di board (bukan per siswa).

### 2. Frontend — `StatusBadge` (`piket-board-view.tsx:119-164`) — tambah kategori "Alfa"

- Field baru `kategoriLive` dari response dipakai MENGGANTIKAN logic penentuan badge saat ini (yang sebelumnya infer dari `status`+kondisi lain secara terpisah-pisah di frontend) — SEDERHANAKAN: frontend TINGGAL switch berdasarkan `kategoriLive` yang sudah final dari backend (kecuali prioritas Terkunci/Belum Memiliki Kartu yang mungkin tetap dicek terpisah di frontend, PUTUSKAN saat implementasi mana yang lebih bersih — bisa juga backend yang urus SEMUA prioritas termasuk Terkunci/Belum Memiliki Kartu langsung di `kategoriLive`, REKOMENDASI: pindahkan SEMUA logic prioritas ke backend supaya 1 sumber kebenaran, frontend murni render map warna+label).
- Badge baru "Alfa" — warna **merah/danger** (bukan warna hijau/sukses tentu saja, KONSISTEN dengan kategori Alfa di rekap/TV Piket yang sudah pakai warna danger — cek `packages/ui` token warna yang sudah dipakai `TvPiketService`/`bar-persentase.tsx` untuk konsistensi visual, JANGAN pilih warna baru sembarangan).
- **Baris `alfa` TIDAK boleh disembunyikan** dari tabel (BEDA dari baris `hadir` yang sengaja disembunyikan via `visibleBoard` filter baris 221 — alfa JUSTRU salah satu kategori PALING PENTING bagi piket untuk ditindaklanjuti, harus tetap terlihat).
- **Real-time transisi** — TIDAK perlu logic baru: begitu event socket `onKampusUpdate` (baris 237-255) datang dengan `status` baru non-null → re-fetch ATAU update state lokal MELIPUTI `kategoriLive` juga (bukan cuma `status` mentah) — pastikan handler socket existing DIPERLUAS untuk update field baru ini, bukan cuma field lama. Sama untuk `handlePermitSubmitted()` (baris 257-262).
- **Transisi "Belum Hadir" → "Alfa" murni karena WAKTU berjalan** (bukan event data) — BEDA dari transisi lain yang dipicu event socket/submit. Ini butuh mekanisme TERPISAH: `setInterval` client-side (misal re-evaluasi tiap 1 menit, ATAU re-fetch board penuh tiap interval tertentu — putuskan mana yang lebih murah: re-hitung `kategoriLive` di frontend berdasar `jamMulai` yang dikirim sekali dari backend per kelas, VS re-fetch board API berkala). **REKOMENDASI**: backend kirim juga field `jamMasukKelas: Record<number, string>` (map kelasId → jamMulai) di response board SEKALI, frontend re-evaluasi `kategoriLive` lokal tiap interval pendek (misal 60 detik) TANPA re-fetch API penuh — lebih murah daripada polling API tiap menit. PUTUSKAN saat implementasi, TAPI PASTIKAN mekanisme SATU inilah yang dipilih dan konsisten (jangan dua-duanya sekaligus/tumpang tindih).

## Edge Cases
- Siswa dengan kartu tapi belum PERNAH tap di kampus itu sepanjang tahun ajaran ini (bukan cuma hari ini) — TIDAK ADA perbedaan perlakuan khusus, logic sama (cek record HARI INI saja, sesuai board yang memang scoped harian).
- Siswa PKL (dikecualikan total dari board, `pklRecords: { none: { endedAt: null } }` sudah difilter di query awal baris 336-354, TIDAK diubah) — TIDAK relevan untuk kategori Alfa, sudah tidak muncul di board sama sekali.
- Hari ini adalah hari SEKOLAH TAPI belum ada baris `jam_sekolah` SAMA SEKALI untuk hari itu (Default Global pun kosong, setelah resolusi 3-lapis T145 tetap `null`) — `kategoriLive` TIDAK PERNAH "alfa" untuk kasus ini (konsisten `determineStatus()` yang fallback ke `hadir` kalau tidak ada schedule — TIDAK diubah task ini, "Belum Hadir" tetap ditampilkan selamanya sampai siswa tap, bukan berubah jadi Alfa).
- Waktu TEPAT PAS deadline (misal `now === jamMulai` persis ke detik) — pakai perbandingan `now > deadline` (strict greater-than, KONSISTEN dengan `determineStatus()` yang juga `scannedAt > deadline` untuk Terlambat) — pastikan operator perbandingan SAMA PERSIS di kedua tempat.

- **Keputusan desain — `jamMasuk` per-baris, BUKAN `jamMasukKelas` map terpisah**: spec merekomendasikan map top-level `Record<kelasId, jamMulai>` di response.
