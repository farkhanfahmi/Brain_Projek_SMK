# T144 — Fix Bug: Alfa Selalu 0 di Rekap (resolveHariWajib Gagal Diam-Diam) + Jaminan Tahun Ajaran Aktif

## Depends on
Tidak ada dependency teknis. Independen, PRIORITAS TINGGI (bug produksi aktif dilaporkan user — rekap alfa selalu 0 walau banyak siswa tidak tap).

## Objective
Kolom Alfa di SEMUA fitur rekap/laporan kembali menghitung dengan benar. Perbaikan 2 lapis: (1) cegah kondisi "tidak ada `AcademicYear` aktif" terjadi lagi (constraint struktural), (2) kalaupun somehow terjadi lagi, sistem tidak diam-diam menghasilkan alfa=0 tanpa tanda apa pun — melainkan memberi sinyal jelas (log/warning/indikator) yang membedakan "memang hari libur" dari "sistem salah konfigurasi".

## Context — Bug Dikonfirmasi (Riset 2026-08-08, Baca Kode + Data Langsung)

User melaporkan: "ketika saya rekap semua alfa 0 padahal banyak siswa yang tidak tab absen ketika datang". Root cause DIKONFIRMASI PASTI (bukan dugaan):

**`resolveHariWajib()` (`apps/api/src/attendance/attendance-report.service.ts:502-535`) adalah SATU-SATUNYA sumber "hari wajib" untuk perhitungan alfa di SELURUH sistem** — dipakai oleh 4 caller: `report()` (baris 115, dipakai rekap admin+dashboard Wali Kelas), `riwayatCatatan()` (baris 417, dipakai halaman detail siswa), `TvPiketService.hitungPersentase()` (tv-piket.service.ts:98), `TvPiketService.hitungSiswaTidakHadir()` (tv-piket.service.ts:140).

Method ini query `AcademicYear.findMany({ where: { isActive: true, tanggalMulai: {lte: to}, tanggalSelesai: {gte: from} } })` — kalau HASILNYA KOSONG (tidak ada baris `AcademicYear` dengan `isActive=true` yang overlap rentang tanggal rekap), maka `wajibDates` (Set tanggal "hari wajib") jadi **KOSONG TOTAL**, dan SEMUA loop yang menghitung alfa berdasarkan `wajibDates` (`report()` baris 213-221, `riwayatCatatan()` baris 481) **tidak pernah jalan** — alfa selalu 0 untuk SIAPA PUN, TANPA error, TANPA warning. Kolom Hadir/Izin/Sakit tetap benar (dihitung langsung dari record, tidak bergantung `wajibDates`) — jadi rekap TERLIHAT normal, cuma alfa yang diam-diam mati.

**Kenapa kondisi "tidak ada AcademicYear aktif" bisa terjadi**: `AcademicYearsService.create()` (`apps/api/src/calendar/academic-years/academic-years.service.ts:28-37`) membuat baris baru dengan `isActive` **default `false`** — TIDAK otomatis aktif. `activate(id)` (baris 39-49) MENJAMIN maksimal 1 aktif (transaksi: matikan semua, aktifkan 1), TAPI **tidak pernah memaksa MINIMAL 1 aktif**. Tidak ada constraint DB (`@@unique` terkait `isActive`) yang mencegah kondisi "0 aktif". Jadi kalau admin lupa klik "Aktifkan" setelah membuat tahun ajaran baru (atau seed data awal tidak menjalankannya), sistem diam-diam kehilangan kemampuan menghitung alfa — **selamanya, sampai admin sadar dan klik aktifkan manual**, dan bahkan setelah itu, rekap untuk PERIODE SEBELUM diaktifkan tetap akan menunjukkan alfa=0 (karena `resolveHariWajib` hanya lihat status `isActive` SAAT QUERY dijalankan, bukan histori).

**Verifikasi lapangan**: dicek di DB dev (bukan production) — `academic_years` benar-benar 0 baris, mengonfirmasi skenario ini nyata terjadi di environment ini. User tidak sempat diverifikasi ulang ke DB production karena tidak ada akses langsung saat diskusi, TAPI user mengonfirmasi ingin lanjut perbaikan tanpa verifikasi tambahan (kemungkinan besar situasi sama).

**Catatan penting BUKAN bug terpisah**: tidak ada toggle manual "tandai alfa" di dashboard piket — ini **sesuai desain** (alfa murni kalkulasi otomatis "hari wajib tanpa record/izin", bukan status yang di-set tangan, sesuai aturan permanen proyek "Alfa → bukan kolom DB"). JANGAN menambahkan toggle manual sebagai bagian dari fix ini — itu bertentangan dengan arsitektur yang sudah disepakati.

## Spec Detail

### 1. Constraint struktural — jamin selalu ada 1 AcademicYear aktif (lapis pencegahan)

- **Migration data**: kalau saat migration dijalankan ternyata ada 0 baris `AcademicYear.isActive=true` DAN ada minimal 1 baris `AcademicYear` di tabel — aktifkan otomatis baris yang `tanggalMulai`/`tanggalSelesai` paling mencakup TANGGAL HARI INI (atau kalau tidak ada yang mencakup hari ini, baris dengan `tanggalMulai` paling baru/terkini) sebagai bagian dari migration data (bukan cuma schema). Kalau TIDAK ADA baris `AcademicYear` sama sekali di tabel — TIDAK BISA auto-fix (tidak ada data untuk diaktifkan), LOG PERINGATAN JELAS saat migration selesai (`console.warn` di script migration atau catatan di summary) memberitahu admin harus membuat+mengaktifkan tahun ajaran secara manual.
- **`AcademicYearsService.create()`** (baris 28-37) — TAMBAHKAN logic: kalau ini adalah baris `AcademicYear` PERTAMA yang pernah dibuat di sistem (`count() === 0` sebelum insert), otomatis set `isActive: true` untuk baris ini (bukan default `false`) — supaya sistem yang baru di-setup dari nol TIDAK PERNAH berada di kondisi "0 aktif" tanpa sengaja. Untuk baris ke-2 dst, TETAP default `false` seperti sekarang (perilaku existing, admin yang putuskan kapan pindah tahun ajaran).
- **`AcademicYearsService.activate(id)`** — TIDAK diubah (sudah benar, menjamin maksimal 1 aktif). TIDAK PERLU endpoint "deactivate tanpa activate yang lain" — kalau endpoint semacam itu ada, VERIFIKASI apakah bisa dipanggil untuk membuat kondisi "0 aktif" secara sengaja; kalau ADA endpoint begitu, TAMBAHKAN guard menolaknya (return error jelas "tidak bisa menonaktifkan tanpa mengaktifkan tahun ajaran lain") — cek dulu apakah endpoint ini benar ada sebelum menambah guard yang tidak perlu.

### 2. `resolveHariWajib()` — bedakan "hari libur legitimate" dari "sistem salah konfigurasi"

Ubah signature/return method ini supaya PEMANGGIL bisa membedakan 2 kondisi berbeda (BUKAN mengubah cara alfa dihitung, murni menambah SINYAL):

- Tambah pengecekan terpisah: `const adaTahunAjaranAktif = await this.prisma.academicYear.count({ where: { isActive: true } }) > 0;` (cek GLOBAL, tidak terikat rentang `[from,to]` — supaya bisa deteksi kondisi "benar-benar 0 aktif di seluruh sistem" vs "ada yang aktif tapi rentang tanggalnya tidak overlap periode rekap yang diminta", 2 kondisi ini beda arti: yang pertama adalah bug config, yang kedua legitimate (misal user rekap tanggal tahun 2020 sebelum sistem dipakai)).
- Kalau `adaTahunAjaranAktif === false` — method ini (atau caller-nya) **WAJIB** mencatat warning eksplisit (`console.warn`/log terstruktur, sertakan pesan jelas: `"Tidak ada AcademicYear aktif saat menghitung hari wajib — kalkulasi Alfa akan menghasilkan 0 untuk semua siswa"`). REKOMENDASI: implementasikan sebagai return value tambahan bukan cuma log side-effect, misal `{ wajibDates: Set<string>, adaTahunAjaranAktif: boolean }` — supaya UI/response API BISA menampilkan indikator eksplisit ke admin (lihat poin 3), bukan cuma log yang tidak terlihat user.
- **SEMUA 4 caller** (`report()`, `riwayatCatatan()`, `TvPiketService.hitungPersentase()`, `TvPiketService.hitungSiswaTidakHadir()`) — update untuk terima struktur baru ini. `wajibDates` tetap dipakai PERSIS SAMA seperti sekarang untuk kalkulasi (TIDAK ada perubahan LOGIC kalkulasi alfa itu sendiri — cuma penambahan sinyal warning), pastikan tidak ada regresi ke kalkulasi yang sudah benar.

### 3. Response API rekap — sertakan indikator "tidak ada tahun ajaran aktif"

- `report()`/`report-flexible` (endpoint yang dipakai `rekap-view.tsx`) — tambah field baru di response, misal `peringatan: string | null` — isi pesan jelas kalau `adaTahunAjaranAktif === false` saat rekap dijalankan (misal `"Tidak ada Tahun Ajaran yang aktif — kolom Alfa mungkin tidak akurat. Hubungi admin untuk mengaktifkan Tahun Ajaran yang sesuai."`). `null` kalau kondisi normal.
- Frontend `rekap-view.tsx` — kalau `peringatan` tidak null, tampilkan banner/alert jelas di atas tabel hasil (warna warning, bukan error merah — ini bukan crash, cuma data tidak akurat) — supaya admin LANGSUNG tahu kenapa alfa terlihat 0/aneh, tidak perlu lapor bug lagi seperti kasus ini.

## Edge Cases
- Rekap untuk PERIODE HISTORIS yang MEMANG sebelum sistem AbsenSI dipakai sekolah ini (misal coba rekap tahun 2015) — `adaTahunAjaranAktif` global TETAP `true` kalau ADA tahun ajaran aktif SEKARANG (baris lain), tapi rentang `[from,to]` yang diminta tidak overlap manapun — ini KONDISI NORMAL (`wajibDates` untuk rentang itu memang kosong, bukan bug), JANGAN tampilkan `peringatan` untuk kasus ini — pengecekan `adaTahunAjaranAktif` di poin 2 SENGAJA global (bukan scoped ke `[from,to]`) supaya bisa membedakan 2 kasus ini.
- Migration data (poin 1) dijalankan di database yang PUNYA beberapa `AcademicYear` tapi TIDAK ADA yang overlap tanggal hari ini (misal semua tahun ajaran yang ada sudah lewat/expired) — auto-aktifkan yang `tanggalMulai` PALING BARU di antara yang ada (paling mendekati "sekarang"), JANGAN biarkan 0 aktif kalau ada minimal 1 baris untuk dipilih.
